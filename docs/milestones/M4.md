# M4 brief: Signatures II. PAdES B-T timestamps, DocMDP certification and modification policy, visible signatures

This brief is the source of truth for M4. It refines `docs/ROADMAP.md` § M4.

**Design references**
- `docs/ARCHITECTURE.md`:
  - §A.4: layering. `folioxide-content` is L4, and `folioxide-sign` depends on model + content.
  - §A.6.1: the update layout.
  - §A.6.2: sizing (`tsa_reserve`).
  - §A.6.4: timestamps.
  - §A.6.5: two-phase signing.
  - §A.6.6: DocMDP.
  - §A.6.7: verification and modification, as updated after M3.
  - §A.7: Node.
  - §A.9: oracles.
  - §A.10: traps #13, #14, #18 and #19.
- `docs/milestones/M3.md`: the binding contracts of §3, the byte layout of §4, V0–V12 in §5, the deliberate-differences table in §0.1, and the V10 whitelist.
- **Decisions that apply:**
  - D10 (M3 D-1 … D-19): pyHanko is the reference, our verdict is never more lenient than pyHanko, and each deliberate difference gets a corpus row.
  - D12 (M3 hardening): a whitelist classifier.
  - **D12.10: M4 QA must include an independent adversarial pass on the classifier** (§5.5).
- **Lessons applied (team.md):**
  - M1 "reference behaviour up front": §0.
  - M1 "linear by construction": every new parser and every new rule is a single bounded pass.
  - M3 "security classifiers are whitelist-based from day one": §5.1–§5.3 enumerate allowed keys. Nothing is a blacklist.

**Goal**
1. **PAdES B-T:**
   - RFC 3161 signature timestamps, with our own DER types.
   - A synchronous `Timestamper` trait, and a two-phase path for async hosts (Node `timestamp` callback).
   - Response validation, and embedding as the unsigned attribute `id-aa-signatureTimeStampToken`.
   - Verification of signature timestamps and of `/DocTimeStamp` dictionaries. M3 only listed them.
2. **DocMDP:**
   - Certification signatures with P = 1, 2 or 3 (first-signature rule, `/Reference`, `/Perms`).
   - Refusals that keep certified documents valid.
   - A modification policy with per-P `docmdp_ok`, whitelisted form filling of non-signature fields, and an Annotations level for P = 3 (decision D-1).
3. **Visible signatures:**
   - A minimal `folioxide-content` builder: content operators, standard-14 metrics, WinAnsi, JPEG passthrough.
   - A signature appearance layout and a widget with a real `/Rect` and `/AP /N`, in the signature's own incremental update. Rotated pages are handled.
4. **Node:** a `timestamp` callback, `certify`, `appearance` and the report's timestamp fields.

**Out of scope**
- LTV, `/DSS`, B-LT and B-LTA, creating document timestamps, and B-T reached through a later document timestamp (M11).
- FieldMDP and `/Lock` (M11). A signature's own FieldMDP turns generic form filling off (§5.1 F0).
- Embedded TrueType/OpenType fonts in appearances (M7), and CMYK JPEG (D-17).
- Signing encrypted documents (M5).
- Generic form-fill APIs (M8). M4 *classifies* form filling made by others; it does not fill.
- Page templates (P = 2 permits instantiating them, but any page-tree change stays `Other`).

### 0.3 Residuals (levels below `Other` whose change a viewer can still show)

These are M3 §0 plus M4.

Every residual below assumes the bytes read the same in every reader. Since QA round 3 (manager rulings R-12 and R-13, §5 V10) that is checked for the lexical differentials of V10 (not for every way two readers can differ): a level below `Other` needs every object the decision reads to pass the canonical-input gate, and a page rule needs a page tree every reader walks the same way. Viewers that read non-canonical bytes in yet another way (PDFium reads `++6`, `4294967296`, `-2147483648` and an integer padded to 256 characters as 0) therefore see only revisions that are `Other`. Since QA round 4 an update after the signed revision must also hold nothing but the bodies its cross-reference section lists where it lists them, its section and `startxref` (finding 3), so a reader that rebuilds the cross-reference data finds the same objects. Since QA round 5 (manager rulings R-17, R-18 and R-21) that is rebuild-proof: the final `startxref` lies within the last 1,024 bytes and at most two EOL bytes follow the final `%%EOF` (poppler rebuilds when it cannot find `startxref`, findings 10 and 13); no line of the update, its stream data and strings included, starts like an object header or `trailer` where poppler looks (a line start, a 255-byte piece of a longer line, after an `endobj`), or like `xref` or `startxref` at a line start or after an `endobj`, and no object header or `trailer <<` is written as words anywhere (PDFium, pdf.js; final fix round 2, finding 3); the store needed no repair; a new object stream holds only members its own revision lists in it at their index (finding 27: PDFium's rebuild takes an unlisted member as a real object); and a table written after the signed revision has canonical subsection headers and exact 20-byte entries (findings 11 and 30); and, since the closing round (finding 13, ruling R-26), every later trailer's `/Size` is a direct integer above every object number the file lists and not below the previous one, so a reader that keeps only the objects below the newest `/Size` (PDFium, from the expert's recollection) drops none. New `/Rect`, `/BBox`, `/Matrix` and geometry numbers are within ±10^5, and so is the `/BBox` mapped through the `/Matrix` (findings 4, 13, 28 and 31), and that box's largest coordinate times its scale onto the `/Rect` is at most 2^20 (final fix round 2, findings 2 and 4), where single-precision readers (PDFium) place them as Folioxide does, to within 1/16 unit. Not covered: pdf.js's rebuild (`XRef.indexObjects`, which runs only when the cross-reference data cannot be read) also ends an object body at a word `xref` inside a line, a string's included, and then skips to the next `startxref`; a fill value such as `see xref table` (allowed since finding 3, as for pyHanko) would hide the update's later objects from such a rebuild. Folioxide's rules leave pdf.js nothing to rebuild for (R-17 (a)–(c), R-21), and pdf.js is not installed (R-16).

**`FormFilling`:**
- A filled field shows any text the filler chooses **inside the widget's `/Rect`**. The `/Rect` never moves (F1). The appearance is clipped to `/BBox`, which §12.5.5 maps onto `/Rect`. A field whose signed widget sets NoZoom or NoRotate is not filled at this level (F0; QA round 2 finding 32): viewers draw such a widget at a fixed size, or upright at its `/Rect`'s corner (§12.5.3), not inside the `/Rect`.
- An opaque filled field can cover signed page content underneath its rectangle. That is inherent to forms; pyHanko and Acrobat allow it.
- A filled field's new or rewritten appearance stream is a form XObject with a direct `/BBox` (QA round 1 finding R5): PDFium does not clip one without it. Its `/BBox` and `/Matrix` numbers are within ±10^5, and so are the `/BBox` corners mapped through the `/Matrix` (QA round 4 finding 4, QA round 5 findings 28 and 31, R-21), whose largest coordinate times the scale onto the widget's `/Rect` is at most 2^20 (final fix round 2, findings 2 and 4: single precision).
- M3's residuals: the visible signature appearances of later signers show inside their `/Rect` only. Their widget's `/Rect` is four finite numbers (QA round 2 findings 4 and 6), written canonically (R-12, QA round 3 finding 12) and within ±10^5 (QA round 4 finding 13, R-21), its appearance mapped onto it precisely in single precision (final fix round 2, findings 2 and 4), its keys are whitelisted (finding 23, §5.3), its flags are whitelisted (no NoZoom, NoRotate, Hidden, NoView or ToggleNoView, R-3; for an existing empty field too, finding 5) and its appearance is a new form XObject with a `/BBox`. Inside the `/Rect` a later signer still draws what it likes.
- New `/DR` names: **closed conservatively** (F7; QA round 1 finding 9). A name may not be added when any signed `/DA` or any signed appearance stream, read with every content stream it draws (form XObjects, tiling patterns and Type 3 glyph procedures, nested; QA round 2 finding 22; the soft-mask groups and the `/Font` Type 3 fonts of its graphics states, QA round 3 findings 6 and 21; a `/Subtype` written through a reference, QA round 4 finding 12), uses it, decoded or as written. When such a stream's own `/Resources` is missing, or lacks any of the categories `/Font`, `/XObject`, `/Pattern`, `/ExtGState`, `/ColorSpace`, `/Shading` and `/Properties` (QA round 5 finding 29: PDFium falls back to the page's resources for a missing category), the resources of every page and every page-tree node are read too, inherited along both the `/Kids` walk and each page's `/Parent` chain (poppler inherits along the first, PDFium along the second), with every stream they draw. So the viewer fallback to `/DR` (poppler 24.02 and PDFium do not fall back; pdf.js and MuPDF unprobed) cannot pick up a new resource for a name a signed stream draws. A new `/DR` name no signed stream uses changes nothing a viewer draws.
- **JavaScript calculation, format and validation** (QA round 5 finding 8, R-23): a signed field's `/AA` `/C`, `/F`, `/V` and `/K` actions, and the AcroForm `/CO` calculation order, run in a JavaScript-capable viewer (Acrobat; not probed) on the filled value, so a filled field can change what another field displays, or how the filled value displays, beyond what F1–F4 compare. pyHanko allows it too; poppler and PDFium run no JavaScript and draw the stored appearances. No precondition is added: this is a residual only.
- **Shared `/Annots` arrays** (QA round 5 finding 9): a later signature widget added to an indirect `/Annots` array that several pages share shows on each of those pages, inside its `/Rect` as each page maps it, although its `/P` names one page. An `/Annots` array of more than one page that gains a markup annotation is `Other` (§5.2), so D-1 does not reach this.

**`Annotations` (D-1):** a whitelisted markup annotation renders **inside its `/Rect`** at 100 % zoom in every viewer probed (manager ruling R-2), given canonical numbers (R-12: PDFium reads a `/Rect` coordinate of `4294967296` as 0, 40,800 pixels outside, so such a `/Rect` is `Other`) and a consistent page tree (R-13). It needs an `/AP /N` form XObject with a `/BBox`, so no viewer synthesizes one. Its geometry (`/QuadPoints`, `/InkList`, `/L`, `/Vertices`, `/Path`, `/CL`, with `/RD`, `/BE` and the border width) lies inside the `/Rect`, given as direct arrays of direct numbers and read within a work budget (QA round 2 finding 1), and NoZoom and NoRotate are refused. poppler regenerates a Highlight from `/QuadPoints` even with an `/AP`, and the geometry check is what confines it (its caps reach a quarter of the quadrilateral's height). Inside its `/Rect`, an opaque annotation can still cover signed content: that is what P = 3 grants.
- **Text is the exception** (QA round 2 finding 7). ISO 32000-2 §12.5.6.4 makes a Text annotation behave as if NoZoom and NoRotate were set, whatever its `/F`, so a viewer draws it upright and unscaled from its `/Rect`'s upper-left corner. On a rotated page that is outside the `/Rect`, so Text is allowed only on a page whose effective `/Rotate` is 0 (§5.2 A2), inherited along a page tree whose `/Kids` walk and `/Parent` chain agree (R-13; QA round 3 finding 11: poppler inherits a root's `/Rotate 90` along `/Kids` for a page without `/Parent` and paints 8,408 pixels outside, PDFium follows `/Parent` and draws it upright). On such a page a viewer that implements NoZoom still draws the note at its unscaled size when zoomed out below 100 %, so it can extend past the `/Rect` there (poppler does not implement it: no spill at 24 to 288 dpi; Acrobat unprobed). What spills is the note's own appearance, at the size of its `/Rect`.

**Timestamps:** unsigned attributes are not signed and `/Contents` is outside the ByteRange. So **anyone can remove or replace the signature timestamp of the last signature in place**. pyHanko behaves the same, and LTA covers it in M11.
- Replacing it needs a trusted TSA token over the same signature value, which can only post-date the original.
- Removing it downgrades B-T to B-B.
- The report says what is there now.
- `genTime` means something only when `timestamp.trusted == Some(true)`.
- **Document timestamps under P = 1** (final fix round 2, finding 3; expert): a timestamp's window is judged with the P in force for markup annotations only. Under a P = 1 certification, a document timestamp followed by a form fill, an `/Info` or XMP change or an approval signature reports `formFilling` or `ltaUpdates` with `docmdp_ok` `None`, pyHanko's level too, so `is_acceptable(FormFilling)` accepts that report although ISO 32000-2 §12.8.2.2 (P = 1: "No changes to the document shall be permitted") forbids the change. Only the certification's report shows it (`docmdpOk` false); a caller gating on the newest report alone misses it. Criterion (i) holds (pyHanko parity). Making such a timestamp entry `other` would be stricter and safe; it is left to D14 (DECISIONS D14 item 13, as proposed in final fix round 2: pyHanko parity in M4, the stricter variant on the ROADMAP verification-hardening backlog).
- **Retired TSA keys** (QA round 1 finding F8): without a validation time, a TSA path is validated at the token's own `genTime` and the signer at that `genTime` (V7b step 9, V9, D-7). That time is the TSA's claim, so a TSA key that outlived its certificate can sign a token claiming a time inside the certificate's validity, and the token and the signer are then trusted. Both carry a warning in the report; a caller (and the Node binding, which passes "now" by default) breaks the circle with a validation time.

## 4. Byte-level and DER-level specification

### 4.1 RFC 3161 types (§2.4.1, §2.4.2; RFC 5816 for ESSCertIDv2)
```
TimeStampReq ::= SEQUENCE { version INTEGER {v1(1)}, messageImprint MessageImprint,
    reqPolicy TSAPolicyId OPTIONAL, nonce INTEGER OPTIONAL, certReq BOOLEAN DEFAULT FALSE,
    extensions [0] IMPLICIT Extensions OPTIONAL }
MessageImprint ::= SEQUENCE { hashAlgorithm AlgorithmIdentifier, hashedMessage OCTET STRING }
TimeStampResp ::= SEQUENCE { status PKIStatusInfo, timeStampToken TimeStampToken OPTIONAL }
PKIStatusInfo ::= SEQUENCE { status PKIStatus, statusString PKIFreeText OPTIONAL, failInfo PKIFailureInfo OPTIONAL }
PKIStatus ::= INTEGER { granted(0), grantedWithMods(1), rejection(2), waiting(3), revocationWarning(4), revocationNotification(5) }
PKIFreeText ::= SEQUENCE SIZE (1..MAX) OF UTF8String
PKIFailureInfo ::= BIT STRING { badAlg(0), badRequest(2), badDataFormat(5), timeNotAvailable(14),
    unacceptedPolicy(15), unacceptedExtension(16), addInfoNotAvailable(17), systemFailure(25) }
TimeStampToken ::= ContentInfo   -- id-signedData; eContentType id-ct-TSTInfo; eContent = DER TSTInfo
TSTInfo ::= SEQUENCE { version INTEGER {v1(1)}, policy TSAPolicyId, messageImprint MessageImprint,
    serialNumber INTEGER, genTime GeneralizedTime, accuracy Accuracy OPTIONAL,
    ordering BOOLEAN DEFAULT FALSE, nonce INTEGER OPTIONAL, tsa [0] GeneralName OPTIONAL,
    extensions [1] IMPLICIT Extensions OPTIONAL }
Accuracy ::= SEQUENCE { seconds INTEGER OPTIONAL, millis [0] INTEGER (1..999) OPTIONAL, micros [1] INTEGER (1..999) OPTIONAL }
```
**Writing the request (D-11):**
- `hashAlgorithm` is `{SHA-2 OID, NULL}`, exactly what `openssl ts -query` writes (probe dump above). On verify, both NULL and absent parameters are accepted (RFC 5754 §2).
- `certReq` is `TRUE` and is written explicitly: `01 01 FF`, since DER omits a DEFAULT only when the value equals it.
- The nonce is a positive minimal INTEGER.
- No extensions.

**Golden** `tst_request_der_golden`: the SHA-256 of the 9 bytes `folioxide` (`069936fe…8a6b`, checked with `openssl dgst`), nonce `0x0102030405060708`, no policy. The bytes match the layout of `openssl ts -query -cert` (asn1parse above):
```
30 43 02 01 01
      30 31 30 0D 06 09 60 86 48 01 65 03 04 02 01 05 00
            04 20 06 99 36 FE 77 E3 F0 82 73 2C 2B FC 9B C3 86 5C E0 1C A9 62 1F D1 E9 B1 AD 09 DA CF 2A 0B 8A 6B
      02 08 01 02 03 04 05 06 07 08
      01 01 FF
```
- With nonce `0x8000000000000000` the nonce becomes `02 09 00 80 00 00 00 00 00 00 00` and the outer length `0x44`.
- With policy `1.2.3.4.1`, `06 04 2A 03 04 01` goes between messageImprint and nonce.

**OIDs (DER content octets):**

| OID | Bytes |
|---|---|
| id-ct-TSTInfo | `2A 86 48 86 F7 0D 01 09 10 01 04` |
| id-aa-signatureTimeStampToken | `2A 86 48 86 F7 0D 01 09 10 02 0E` |
| id-aa-signingCertificate (v1) | `… 10 02 0C` |
| id-aa-signingCertificateV2 | `… 10 02 2F` |
| id-kp-timeStamping | `2B 06 01 05 05 07 03 08` |
| extKeyUsage | `55 1D 25` |

**`genTime`** (RFC 3161 §2.4.2), with our own parser (R-3):
- The form is `YYYYMMDDhhmmss[.f{1,9}]Z`. The dot is required before a fraction, and the string ends in `Z`.
- Seconds above 59, other time zones and missing `Z` give `TimestampMalformed`.
- A fraction with trailing zeros is accepted with a warning (the RFC says MUST NOT).
- **Never** use `der::asn1::GeneralizedTime`, which requires exactly 15 bytes.

**Parsing:**
- The M3 raw TLV walker: BER and DER, depth ≤ 32, `MAX_CERTIFICATES` and `MAX_ATTRIBUTES` as in M3. Every slice is bounds-checked.
- TSTInfo is decoded from the eContent octets. Constructed OCTET STRINGs are joined with `tlv::octet_string_value`.

### 4.2 Response validation (`validate_response`, called by `finish_with_timestamp`)

Ordered checks. The first failure is `TimestampInvalid(reason)`, and the reason names the check.
1. The response parses. Status must be `granted` or `grantedWithMods` (D-9). Otherwise the reason is "TSA refused: status <n>, \"<statusString>\", failInfo <names>".
2. A token is present.
3. The token is a ContentInfo `signedData` with exactly one SignerInfo, eContentType id-ct-TSTInfo, and eContent present, and passes the V7b step-1 whitelist (QA round 1; its signed attributes in DER and its ESS attributes decoding whole since QA round 3), so Folioxide never embeds a token its verifier calls malformed.
4. The TSTInfo:
   - `version == 1`
   - `messageImprint` equals the request's: the same algorithm OID, with NULL and absent parameters equivalent, and the same hash (RFC 3161 §2.4.2 "MUST have the same value")
   - the nonce is present iff the request had one, with an equal INTEGER *value* (canonical content octets; a non-minimal encoding is no valid INTEGER, X.690 §8.3.2, and step 3 refuses the token since QA round 1)
   - `policy` equals `reqPolicy` when the request had one
   - `genTime` parses
5. The TSA signature: `cms::verify_encapsulated(parsed, OID_CT_TST_INFO, &[])`, which must give `intact && signature_valid` (an `id-RSASSA-PSS` key verifies no PKCS #1 v1.5 token, R-22 (b)). The signer certificate must be in the token: certReq was true, so RFC 3161 §2.4.1 says it "MUST be provided".
6. ESS: a `signing-certificate` (v1, SHA-1 certHash, **not** a weak-algorithm problem here) or `signing-certificate-v2` attribute must be present, and every one present must match the TSA certificate as V7b step 5 checks it (RFC 3161 §2.4.1, RFC 5816); the TSTInfo `tsa` name, when present, names it.
7. `check_tsa_certificate(tsa)` (D-4; its extension list since QA round 5, R-22 (c)).
8. The TSA certificate's validity contains `genTime`.
9. The request in `finish_with_timestamp`:
   - It parses.
   - `cert_req` is true.
   - Its imprint equals `H_alg(normalized signature value)` (§4.5).

### 4.3 The unsigned attribute (RFC 5652 §5.3; RFC 3161 Appendix A; EN 319 122-1 signature-time-stamp)
```
SignerInfo ::= SEQUENCE { 02 01 01, sid, digestAlgorithm, A0 <signedAttrs, unchanged>, signatureAlgorithm,
                          04 <signature value, unchanged>,
                          A1 L { 30 L { 06 0B 2A 86 48 86 F7 0D 01 09 10 02 0E,  31 L { <TimeStampToken, byte-identical> } } } }
```
- **Exactly one** attribute with **exactly one** value is written.
- The signed attributes and the signature value are not touched, so the signer's signature stays valid. Only the lengths of the SignerInfo, the `signerInfos` SET, SignedData, `[0]` and the ContentInfo grow.
- The imprint is computed over the **contents octets** of `signature` (pyHanko `generic_cms.py:792`; OpenSSL `-data sigvalue.bin`).
- **DER:**
  - Our CMS stays DER.
  - A **BER token** is embedded verbatim with a warning (D-12).
  - `is_der_cms` treats the attribute value as opaque, so `ETSI.CAdES.detached` is not refused because of a TSA's encoding.

### 4.4 Placeholder sizing with `tsa_reserve` (refines M3 §4.2 step 1)
```
needed = if tsa_reserve == 0 { cms_len_upper_bound(…) }
         else { cms_len_upper_bound_with_timestamp(sizing_attrs, chain, alg, kind, digest, token_len = tsa_reserve) }
R = contents_reserve.unwrap_or(max(8192, round_up_1024(needed + 512)))     // explicit R < needed → PlaceholderTooSmall
```
- `cms_len_upper_bound_with_timestamp` encodes a dummy token of exactly `token_len` bytes. It is exact for RSA, and ECDSA keeps M3's ≤ 3 bytes of slack.
- At finish, the real length is checked against `R`. `PlaceholderTooSmall { needed: real_len, reserved: R }` is returned **before** anything is written.
- The OpenSSL test token is 3131 bytes (two RSA certificates), so 8192 leaves room for chains of about 3 certificates (R-5).

### 4.5 The two-phase B-T flow
```
prepare(doc, req{tsa_reserve})                     → PreparedSignature (unchanged FXPS v1)
sig = signer(to_be_signed)
req_der = prepared.timestamp_request(sig, params)  // verify_and_normalize(sig) first; imprint = H(normalized value)
resp = TSA(req_der)                                // host: HTTP POST application/timestamp-query
pdf = prepared.finish_with_timestamp(sig, req_der, resp)
```
- **ECDSA:** P1363 input is normalized to DER first, and the imprint covers the DER value that is embedded (R-6).
- `finish_with_timestamp` normalizes again (deterministically) and compares the request imprint.
- `PreparedSignature` stays stateless. The Node slot remembers `req_der`.

### 4.6 DocMDP certification (ISO 32000-2 §12.8.2.2, Table 257 DocMDP transform parameters; Permissions §12.8.6, 32000-1 §12.8.4; field lock Table 236)

**Signature dictionary keys** (M3 §4.1 order, with `/Reference` inserted before `/ByteRange`, so `/Contents` stays last):
```
/Type /Sig /Filter /Adobe.PPKLite /SubFilter /ETSI.CAdES.detached /M (D:…) [/Name …] [/Reason …] [/Location …] [/ContactInfo …]
/Reference [<</Type /SigRef /TransformMethod /DocMDP /TransformParams <</Type /TransformParams /P 2 /V /1.2>>>>]
/ByteRange [0 a b c] /Contents <…>
```
- All direct, exactly as pyHanko writes it (`cms_embedder.py:38-53`).
- `/V /1.2` is a **name** (ISO note).
- No `/Data`, `/DigestMethod` or `/DigestValue`.

**Catalog:**
- `/Perms <</DocMDP S 0 R>>`.
- If `/Perms` exists: a direct dict gets the key added in the catalog edit; an indirect one has that object edited.
- An existing `/UR3` is kept, with the warning "usage-rights signature will no longer validate".
- `/AcroForm /SigFlags 3`, as in M3 (no field is signed yet).

**Rules in `prepare`** (all are `DocMdpForbids` with the rule in the message):
- **(a) Certifying:** refused when any signature field has a `/V` (document timestamps included: "it shall be the first signed field", §12.8.2.2.1). Also refused when the catalog already has `/Perms /DocMDP`, even with no signed field (`certify_twice_rejected`).
- **(b) Approval on a certified document:**
  - P = 1 is refused (M3).
  - P = 2 or 3 is allowed for a new **invisible** field or an **existing empty** field (visible or not).
  - A **new visible** field is refused (D-3). pyHanko marks the certification `OTHER` (probe `p2_approval_visible`).
- **(c)** `certification` together with `appearance` is allowed: it is the certifier's own field.

### 4.7 Visible signature (§12.7.5.5 signature fields, §12.5.6.19 widgets, §12.5.5 appearance streams, §8.10 form XObjects, §7.7.3.3 `/Rotate`)

**Widget:**
- The new merged field/widget is M3 §4.1's, except:
  - `/Rect [llx lly urx ury]`: normalized and rounded as the serializer writes it.
  - `/AP <</N A 0 R>>`.
  - `/MK <</R r>>` when the page rotation `r ≠ 0`.
  - `/F 132` (Print | Locked) stays. No `/A`, `/AA`, `/OC` or `/Parent` (M3 V10 (1)).
- **Validation:**
  - The rect must be finite, of positive area, and must intersect the page's crop box. Otherwise `InvalidArgument`.
  - Its coordinates, width and height must be within ±10^5 (M4 QA round 4, finding 13, and manager ruling R-21: the verifier holds new widgets and appearances to that bound, the `/BBox` mapped through the `/Matrix` too, §5.3 C1). Otherwise `InvalidArgument`; an existing field's `/Rect` too.
- **Existing field:**
  - `rect` must be `None` or equal to the widget's `/Rect`. The `/Rect` is never changed, because changing it is `Other` for earlier signatures.
  - A zero-area widget with an appearance is `InvalidArgument`.
  - A field whose widget is a separate `/Kids` object with an appearance is `Unsupported` (D-18; pyHanko's rule covers only the field's own `/AP`).

**Appearance XObject:**
```
<< /Type /XObject /Subtype /Form /BBox [0 0 W H] [/Matrix M] /Resources << /Font << /F1 F 0 R >> [/XObject << /Im1 I 0 R >>] >> /Filter /FlateDecode /Length n >>
```
- **Visual size:** `(W, H) = (w, h)` of the rect for r ∈ {0, 180}, and `(h, w)` for r ∈ {90, 270}.
- **`/Matrix`**, so that §12.5.5's transformed BBox has exactly the rect's size. The algorithm's step b then only translates. Verified upright with poppler for all four rotations; `/Rotate` turns the page **clockwise** on display, so the appearance turns counter-clockwise:

| r | `/Matrix` |
|---|---|
| 0 | omitted (identity) |
| 90 | `[0 1 -1 0 H 0]` |
| 180 | `[-1 0 0 -1 W H]` |
| 270 | `[0 -1 1 0 0 W]` |

- `/Resources` belong to the stream itself, never `/DR`, which keeps clear of M3 residual 2.

**Layout:**
- **Insets and border:** the padding is `p = min(2, W/20, H/20)`. When `border_width > 0`, the border is `bw w 0 G bw/2 bw/2 W-bw H-bw re S`, and the text area is inset by `bw`.
- **Image `Left`:**
  - Column width `iw = min((H−2p)·img_w/img_h, (W−2p)/2)`.
  - The image is drawn by `q sx 0 0 sy x y cm /Im1 Do Q`, keeping its aspect ratio and vertically centred.
  - The text starts at `x = p + iw + p`.
- **Image `Background`:** the image is fitted (contain) and centred, drawn before the text, with no transparency.
- **Text lines** (`Default`), each line encoded WinAnsi:
  - `Digitally signed by <name>`, where name = `options.name`, else the signer certificate's CN, else its subject
  - `Date: <YYYY-MM-DD HH:MM:SS ±HH:MM>` from `signing_time` (the claimed time; never `genTime`)
  - `Reason: …` and `Location: …` when given
- **Font size:**
  - Given, or `s = min(12, (H−2p)/(n·1.2))`.
  - If the widest line exceeds the text width, `s` scales down proportionally.
  - Below 4 pt: `s = 4`, and each over-wide line is truncated and ends with `…` (WinAnsi 0x85), with a warning.
- **Baselines:** `y0 = H − p − s·ascent/1000` (Helvetica ascent 718), and each next line is `0 −1.2s Td`.
- **Operators:** `q … [border] [image] BT /F1 s Tf 0 g x y0 Td (l1) Tj 0 -1.2s Td (l2) Tj … ET Q`.

**Fonts (D-16):**
- `font_dict()` writes `/FirstChar 32 /LastChar 255 /Widths [224 ints]` from AFM. PDF 2.0 deprecates the special treatment of the standard 14 fonts, so the widths are written. Since QA round 1 (findings 2, 35) `font_descriptor()` gives the font descriptor too (`/Flags 32 /FontBBox /ItalicAngle 0 /Ascent /Descent /CapHeight /XHeight /StemV` from the AFM), which the appearance writes as an indirect `/FontDescriptor` (ISO 32000-2 Table 109). The font program is not embedded, so a visible signature on a PDF/A document breaks its conformance; embedding is M7.
- **Widths are mapped by glyph name through Annex D WinAnsiEncoding, not by the AFM `C` code**, which is StandardEncoding: `quotesingle` is `C 169` in the AFM but WinAnsi 0x27, and `Euro` is `C -1` but 0x80.
- **Verified values** (Helvetica.afm in PDFBox 3.0.3): space 278, A 667, W 944, quotesingle 191, bullet 350, ellipsis 1000, Euro 556; FontBBox −166 −225 1000 931; Ascender 718; Descender −207; CapHeight 718.

**WinAnsi (Annex D.2):**
- The encoder is Windows-1252, with U+00A0 → 0xA0 and U+00AD → 0xAD.
- The codes cp1252 leaves undefined (0x81, 0x8D, 0x8F, 0x90, 0x9D) are never produced.
- Unmappable characters become `?`, and the warning is "N characters cannot be shown with the standard 14 fonts (embedded fonts: M7)".

**JPEG (§7.4.8, D-17):**
- **Marker walk:**
  - The data starts with `FF D8`.
  - Each segment is `FF xx` plus a big-endian length ≥ 2, within the input. Fill `FF FF` and the standalone markers `D0–D7` and `01` carry no length.
  - The walk stops at SOS (`FF DA`), and an SOF must have come before it.
- **SOF:**
  - **SOF0, SOF1, SOF2** are supported.
  - **SOF3, SOF5–7, SOF9–11 and SOF13–15** are `Unsupported`: lossless, hierarchical and arithmetic coding, which viewers often reject.
  - Precision must be 8.
  - Height 0 (DNL) is `Unsupported`.
  - Nf ∈ {1, 3}. 4 is `Unsupported` in M4 (CMYK: Adobe inversion is unprobed here).
  - The segment length must be `8 + 3·Nf`.
- **APP14 `Adobe`:** `FF EE`, length ≥ 12, `"Adobe"`; its transform byte is recorded.
- **ColorTransform:**
  - With APP14 present, no `/DecodeParms`: §7.4.8 says the marker governs.
  - Three components whose IDs are `'R','G','B'` and no APP14 get `/DecodeParms <</ColorTransform 0>>`, as libjpeg does.
- **XObject:** `/Width /Height /ColorSpace /DeviceGray|/DeviceRGB /BitsPerComponent 8 /Filter /DCTDecode`, with the data in `StreamData::Encoded` unchanged.
- **Limits:** ≤ 16 MiB input, one pass, no allocation proportional to the pixel count.
- EXIF orientation is ignored (documented).
- **Limitation (manager ruling R-24, QA round 5 finding 2):** only the header is parsed; the scan data after SOS is passed through unread. A JPEG whose SOF declares a size its scan data cannot hold (65535 × 65535 with a 4-byte scan, say) is accepted and embedded unchanged, and viewers then draw nothing or an error box inside the appearance. Decoding or sizing the scan is left to the image work of M7.

**V10 (modification).** `Revisions::modification(k, &ModificationContext { certifying: bool, timestamp: bool, permissions })` adds §5.1, §5.2 and §5.3.
- `certifying` is true when the evaluated signature sets DocMDP permissions: it declares DocMDP, or its field's `/Lock` has `/P` (R-4; pyHanko applies `valid_when_certifying` whenever `docmdp_level` is set).

Its `docmdp_ok` stays `None` (R-5).
- **Parser differentials** (manager ruling R-1, QA round 1 findings 5–8 and 11): a revision after the signed one is `Other` when any object it writes holds a dictionary with a duplicate key at any depth (stream dictionaries and objects inside object streams included), when its trailer or cross-reference stream dictionary has one, when an object stream it writes holds a number twice or has a header and offset table that do not describe its data exactly, or when one of its cross-reference sections lists a number twice. The syntax layer still parses last-wins; the sign crate reads the raw bytes with the public lexer and parser (`revisions/differential.rs`).
  - **In the signed bytes too** (QA round 2 finding 8): the evaluated signature's dictionary and its field (with their `/Reference`, `/TransformParams` and `/Lock`) are re-read from their raw bytes, in the file or in an object stream. A key written twice there gives `SigDictAmbiguous` (a new problem code; the report is not valid). An ambiguous `/ByteRange` or `/Contents` makes the signature not intact and its coverage unclear (pyHanko digests the first value, poppler the last). A key written twice anywhere in the `/Reference` array (its entries, their `/TransformParams` and `/P`, direct or indirect) or in the field's `/Lock` makes the declaration `DocMdpInvalid` with P = 1 in force (V11), on the verifying and on the signing side; a dictionary that cannot be re-read counts as ambiguous (fail closed). Since QA round 3 (R-12) "ambiguous" means any defect of the canonical-input gate below, not only a key written twice: `/P 4294967298` or `/P ++2` in a signed declaration is `SigDictAmbiguous` and `DocMdpInvalid` (`docmdp_p_huge_integer`).
  - **The revision chain** (QA round 2 finding 9): when a trailer or cross-reference stream dictionary gives `/Prev` or `/XRefStm` twice with different values, first-wins and last-wins readers follow different revisions, and one of them may never see the signed one. `verify` then returns `Error::Syntax` (`Xref`, "/Prev twice"; `E_XREF` in Node) instead of a report list, rather than report no signatures. Since QA round 3 (finding 13) the signing side refuses such a chain with the same error (`docmdp::certification`, run by `prepare` and `sign`): its last-wins reading could miss a certification that a first-wins reader sees.
- **The canonical-input gate** (manager ruling R-12, QA round 3 findings 4, 5, 7–10, 12, 15–18, 22 and 38–41; `revisions/canonical.rs`). It replaces chasing one parser or lexer differential after another: a level below `Other` is granted only when **every object the decision reads** passes a strict lexical check of its raw bytes. Otherwise the revision is `Other`, with a note naming the object and the defect.
  - **Which objects:** (1) every object revisions `k+1..=r` write: objects inside object streams, the container's own dictionary and its header numbers, the trailers and the cross-reference stream dictionaries included; (2) the **signed** copy (in revision `k`'s view) of every object a later revision changes or re-lists (finding 5: a signed duplicate key read last-wins made a re-listing out of what first-wins readers see as a fill), and the signed objects the form rules read (the field, its ancestors, its widgets, their `/AP` and `/AP /N` dictionaries), the signed `/DR` a new one is compared with and every object the F7 guard reads when a name is added, and every object of revision `k` that the role usage index reads (the objects reachable from its trailer: one that is not canonical counts when its raw bytes, every value of every key, may refer to an object whose role a later revision claims and Folioxide's reading of it does not, or when a reference in it is not canonical; `form_inplace_ap_shared_first_wins`; since QA round 4, finding 1, the walk also follows the raw references of every object that is not canonical, so an object only another reader reaches through it, a first-wins carrier two or more hops away, is read and its uses recorded: `form_inplace_ap_hidden_two_hops`, `_three_hops`); (3) the page-tree nodes a page rule consults (R-13, §5.2 A2). The evaluated signature's own objects (its dictionary, field, `/Lock` and `/Reference` chain) get the same check through `SigDictAmbiguous` above.
  - **Canonical means:** no dictionary, at any depth, writes a key twice; an integer is one optional sign and digits, `[+-]?[0-9]+`, with a magnitude of at most 2,147,483,647 (symmetric, stricter than R-12's −2^31: PDFium reads `-2147483648` as 0, QA variant A2-r3-square-rect-y2-int32-min-cert3) and **at most 11 characters**, the length of `-2147483647` (QA round 4 finding 2: R-12's regular expression allowed any number of leading zeros, and PDFium reads a word of 256 characters or more as 0; `0400` stays canonical, `000000000400` does not); a real is `[+-]?([0-9]+\.[0-9]*|\.[0-9]+)` of at most 40 characters with a magnitude of at most 3.403 × 10^38 (Annex C); a name has no `#00` and no `#` without two hexadecimal digits, and a hexadecimal string holds only hexadecimal digits and white-space (no token the lexer repairs); a reference `N G R` has unsigned integers, within the same length; an object stream lists each number once with increasing offsets inside its data; a cross-reference section lists each number once. A value that does not re-read (a missing delimiter, a keyword other than `true`, `false`, `null`) fails closed.
  - **Why:** Folioxide's lexer (and poppler) read `++6`, `+-260`, `4294967296` or a 21-digit integer as numbers, PDFium reads them as 0; pyHanko cannot read a number with two signs at all. A re-listed signed object respelled that way looked unchanged (`ltaUpdates`) while PDFium and poppler showed a hidden widget (260 pixels outside), and a new widget or annotation `/Rect` ending in `4294967296` was painted by PDFium at y 0 to 300 (29,800 and 40,800 pixels outside).
  - **Cost:** one linear token pass per object (the public `Lexer`, bounded by the store's nesting and string limits), cached per object, entry and container entry, and charged to the modification work budget at one unit per 8 tokens.
- **The update layout** (QA round 4 finding 3; `differential::layout_ambiguity`): each revision `k+1..=r`, from the end of the revision before it to its own end (the end of the file for the newest), holds only object bodies its cross-reference section lists at exactly their position (or its cross-reference stream), read strictly (stream data by `/Length`, `endobj`), then its section (a table from `xref` to the end of its trailer, or the stream) and `startxref` with its offset, with white-space and comments anywhere; every uncompressed entry of the section points at such a body or is the entry in force before it (a re-listing of an older body). Otherwise the revision is `Other`. A body no section lists is invisible to Folioxide, poppler and pyHanko, which follow the section, but a reader that rebuilds the cross-reference data (PDFium does when an entry is 19 bytes or junk precedes `startxref`) takes it for the object (`parser_unlisted_object_body`, `parser_junk_before_startxref`). One pass per revision, cached, charged to the work budget.
  - **Rebuild-proof** (manager rulings R-17 (c), (d) and R-21; QA round 5 findings 10, 11, 13 and 30): poppler rebuilds the cross-reference data when it cannot find `startxref` (`XRef::constructXRef`, line by line), PDFium after a malformed entry (`RebuildCrossRef`), and both then take any text that looks like an object header for an object. So, besides the bodies and the section: an object header is written canonically (unsigned numbers of at most 10 and 5 digits without a leading zero, at most 32 bytes of white-space before and inside it: `parser_fake_object_*`), the store needed no repair and every in-use object the revision writes sits at the offset its entry gives (`Store::check_incremental`), and no text of the revision, stream data, strings, names and comments included, is structure to a rebuilding reader other than what the update writes as its structure (one linear scan, `differential::rebuild_text`; `parser_fake_object_in_ap_stream`, `parser_fake_object_in_value_string`): where poppler's `XRef::constructXRef` looks, that is at the start of every line (`Stream::getLine`: after LF, CR or CR LF), of every 255-byte piece of a longer line, and after every `endobj` in a piece, past spaces, tabs and form feeds, no object header (two digit runs and white-space, then `obj` as a prefix: poppler takes `5 0 objective` for one) and no `trailer` before `<<` or a comment; at a line start or after an `endobj` (where pdf.js's `indexObjects` tokens start) no `xref` and no `startxref`; and anywhere, no object header written as words (`N G obj` with the first digit and the end of `obj` at a word boundary: PDFium's `RebuildCrossRef` reads words, pdf.js's `indexObjects` matches `\b\d+\s+\d+\s+obj\b` inside an object) and no `trailer` written as a word before `<<` or a comment. Final fix round 2, finding 3: the scan matched the keywords at any position before, so an honest fill value such as `see xref table`, `startxref`, `Room 12 3 object`, `Item 4 7 objective` or `trailer <b>` made the signature `other` (pyHanko: `formFilling`); inside a line these are no structure to any of the three readers (`parser_honest_fill_structure_words`, `honest_fill_values_with_structure_words_stay_fills`), while the same words after a raw line break inside the string are (`see\nxref table`, `Room\n12 3 object`: `other`). A table is written canonically (§7.5.4): `xref` and an end-of-line, subsection headers of two unsigned integers of at most ten digits without a leading zero (PDFium reads a padded word as 0: `parser_xref_subsection_padded`), entries of exactly 20 bytes (a 19-byte entry makes PDFium rebuild: `parser_xref_entries_19_bytes`), then `trailer`. A false positive (a content stream that shows the words `12 0 obj`, the word `trailer` before `<<`, a line that starts with `xref`, or a fill value such as `x endobj xref` or `endobj 4 0 obj`, where poppler's scan restarts after the `endobj`) makes a revision `Other`, the fail-closed side (closing round, findings 3 and 5). The scan is linear by construction (closing round, findings 2 and 6, ruling R-27; `differential::RebuildScan`): an object-header candidate that starts inside the number of the last candidate that came out clean reads the same runs and is skipped, so every run of digits or white-space is read at most twice, and the bytes read are work of the verification's budget. Before, every 255-byte piece of one long line of digits read the run to its end: 16 MB took three minutes. `the_rebuild_scan_is_linear_on_16_mb_runs` feeds it 16 MB of digits, white-space, `endobj`, `trailer ` and `%` within 16 steps a byte (it reads about 4), and `parser_ap_stream_long_digit_line` (a 4 MiB digit line in a fill's appearance stream) stays `formFilling`.
- **`/Size`** (manager ruling R-26, closing round finding 13; `differential::size_ambiguity`; ISO 32000-2 §7.5.5 Table 15, §7.5.8.2 Table 17): a later revision's trailer (and a hybrid section's cross-reference stream dictionary) gives `/Size` as a direct integer greater than every object number the sections up to it list (free entries included) and not smaller than the previous revision's `/Size`; otherwise `Other` (`parser_trailer_size_shrunk`, `_shrunk_info_only`, `_off_by_one`; pyHanko's non-strict reader: `formFilling` or `ltaUpdates`, §0.1). PDFium keeps only the objects numbered below the newest `/Size`. A `/Size` above the highest number + 1 (over-declared, non-conforming) drops nothing and passes (`parser_trailer_size_over_declared_info_only`: `ltaUpdates`, as pyHanko). Folioxide's own signer numbers a signature's new objects from that previous `/Size` when it is above `Store::next_object_number()` (a direct integer that leaves room below `Limits::max_objects`), as pyHanko's incremental writer does, so the update's `/Size` (the highest number it lists + 1) is not below it and a co-signature keeps the earlier signatures' level (`parser_trailer_size_over_declared_then_cosigned`: `formFilling`, as pyHanko; final fix round 2 verification, expert finding 1: it was `other`, its `/Size 12` below the previous 100). - **The file's tail** (manager ruling R-17 (a), (b); QA round 5 findings 10, 13 and 16–26; `differential::tail_ambiguity`): the file ends with its last `startxref`, at most 1,024 bytes before the end (poppler's `XRef::getStartXref` window), the newest section's offset, `%%EOF` and at most two end-of-line bytes. After 25 KB of trailing comments, or 40 KB of white-space, NUL or end-of-lines, poppler 24.02 rebuilt and drew object text from an update's appearance stream (469,411 pixels outside the annotation). Otherwise every signature's `modification` is `Other`, the newest signature's too (what follows its `%%EOF` is a change it does not cover): `parser_tail_pad_{lf,space,nul,crlf,comment,mixed}`, `parser_tail_extra_eol`, `parser_startxref_corrupted` (pyHanko cannot read the padded files at all: "EOF marker not found"). A signed file with `\r\n` after `%%EOF\n` is therefore `Other` for the last signature too, and a file ending `%%EOF\n` or `%%EOF\r\n` stays as it was.
- **New object streams** (manager ruling R-18, QA round 5 finding 27; `Revisions::object_stream_check`): every member of an object stream a revision after the signed one writes is listed by a compressed entry of that same revision's section, in that stream at its header index, and the revision writes no other copy of it. A classic table cannot list compressed objects, so a revision written with one adds no non-empty object stream. Each member is then classified like any object of the revision.
- **Shared field appearances** (manager ruling R-19, QA round 5 finding 7; parity with pyHanko's `GenericFieldModificationRule._allow_appearance_update`): when a non-signature field node of the signed revision, terminal or not (closing round, finding 10: pyHanko's `_list_fields` yields every named node, non-terminal parents included; Folioxide checks every node of its field walk), has an indirect `/AP` dictionary whose raw-reference usage count (hidden first-wins carriers included, R-12 (2)) is not exactly 1, every later revision whose level would be above `None` is `Other`, whatever it changes: `form_ap_dict_shared_repointed`, `_unrelated_fill`, `_info_only`, `_hidden_carrier`, `form_ap_dict_shared_nonterminal_parents` and `_nonterminal_parents_cert2` (pyHanko: `other`), with `form_ap_dict_indirect_fill_control`, `form_ap_dict_private_nonterminal_parents` and `_cert2` (one use each: `formFilling`). The same count applies to the indirect `/AP` dictionary of a terminal **unsigned signature field** of the signed revision, but only for a later revision that signs that field (gives it a `/V`), since pyHanko's `SigFieldModificationRule` runs `_allow_appearance_update` only for a field that goes from unsigned to signed (final fix round 2, finding 1): `sigfield_ap_dict_shared_signed_next`, `_visible_next`, `_cert2_then_second` (pyHanko: `other`, docmdpOk false), with the controls `sigfield_ap_dict_shared_control_private` and `_unrelated_fill` (`formFilling`). Stricter than pyHanko, which checks the old dictionary only when the new `/AP` holds `/N`, `/R` or `/D`: whatever the `/AP` becomes. Folioxide's signer warns when it signs an existing field whose `/AP` dictionary another field of the form names, on a document signed already.
- **Page-tree consistency** (manager ruling R-13, QA round 3 findings 11 and 14): a rule that depends on the page (a page's `/Annots` gaining a signature widget or an annotation, the rotation a Text annotation needs) holds only when the page is reached exactly once by the iterative `/Kids` walk from the catalog's `/Pages` (each node reached once, `/Type` `/Pages` or `/Page` or absent; a `/Page` with `/Kids`, or an untyped node with `/Kids` and `/Contents` or `/Annots`, fails: poppler walks it as a page, PDFium as a node, QA round 4 finding 10, `annots_text_page_with_kids`), the root has no `/Parent` and every other node's `/Parent` is the node that lists it in `/Kids`, and the `/Rotate` inherited along that walk (§7.7.3.4) is a direct integer on every node of the path. Otherwise the revision is `Other` ("not on a page every reader places the same way"). poppler inherits along `/Kids`, PDFium along `/Parent`: a page without `/Parent` in a tree whose root has `/Rotate 90` showed a new sticky note 8,408 pixels outside its `/Rect` in poppler and upright inside it in PDFium.
- **XMP** (QA round 1 findings 22, 23, 25, 26): a new or changed `/Metadata` stream must be well-formed XML 1.0 with namespaces whose root is `x:xmpmeta` (pyHanko's `MetadataUpdateRule` parses it with lxml), checked in one linear pass with bounded depth and attribute counts (`revisions/xmp.rs`); the same pass masks the document timestamp's bookkeeping attributes. QA round 2 (findings 18–20 and 24–30, from a differential fuzz against lxml) tightened it: character references have decimal or hexadecimal digits only (no sign); the XML declaration (§2.8) is valid only at the very start, with `version="1.0"`, optionally `encoding="UTF-8"` (any case) and `standalone` `yes` or `no`, in that order, and any other processing instruction whose target is `xml` in any case is refused; every namespace name is an RFC 3986 URI-reference written without entity or character references (an IP-literal host is refused, stricter than lxml); `xml` is bound only to the XML namespace, nothing else to it, `xmlns` never, and the default namespace is neither of the two (Namespaces in XML 1.0 §3). Over 60,000 seeded mutations no packet Folioxide accepts is refused by lxml. QA round 3 (findings 19, 20, 23–37 and 42–54, size-scaled and filter variants the fuzz did not reach):
  - **libxml2 limits:** lxml parses pyHanko's packet without `huge_tree`, so one text node, comment, attribute value, CDATA section, processing instruction or white-space run of 10,000,000 bytes or more is an error there. A packet is XMP to Folioxide only below 10,000,000 bytes in all (`MAX_XMP_BYTES` = 9,999,999), so no single node reaches that limit, and element, attribute, prefix and processing-instruction target names are at most 50,000 bytes (libxml2's `XML_MAX_NAME_LENGTH`; `xmp::MAX_XML_NAME`). The bounded depth (256) already agreed.
  - **Decoding:** the stream is decoded for the check exactly as pyHanko decodes it (`revisions/metadata.rs`), not by the lenient syntax-layer decoder: `/Filter` absent or a chain of `/FlateDecode` (`/Fl`), `/ASCIIHexDecode` (`/AHx`), `/ASCII85Decode` (`/A85`) and `/Crypt` `/Identity`; Flate a complete zlib stream with its header and a matching Adler-32 (trailing bytes ignored, as Python's `zlib.decompress`), with no `/Predictor` other than 1, and no ASCIIHex or ASCII85 filter after a Flate in the chain, whatever lies between (QA round 4 finding 11: pyHanko's FlateDecode returns a `memoryview`, on which its ASCII decoders raise, `metadata_flate_then_ahx`); ASCIIHex and ASCII85 with their end markers (`>`, `~>`), ASCII85 groups within 32 bits; `/Length` equal to the data's length; no `/F`, `/FFilter` or `/FDecodeParms` (§7.3.8.2). Anything else (LZW, RunLength, raw deflate, a wrong Adler-32, a truncated trailer, a missing end marker, Predictor 2) is not XMP, so the change is `Other`, as in pyHanko ("/Metadata XML syntax could not be validated").
- Every explained or classified object also gets a `ChangeClass`:
  - `Relisting`, `Orphan`, `XrefStream`, `Metadata` (Info, XMP, `/Version`, `/Extensions`, `/MarkInfo`)
  - `SignatureField` (a new invisible empty field, `/Ff`)
  - `Signature` (a signature dictionary, a signed field and its appearance, a visible signature field)
  - `DocTimeStamp` (a DTS dictionary, its invisible field, the `/Fields`, `/Annots` and new-AcroForm edits made only for it)
  - `DefaultResources`, `FormFill`, `Annotation`
- The outcome holds the level and the set of classes.

### 5.1 Form-filling whitelist (rule V10 (4′); level `FormFilling`; class `FormFill`)

Written whitelist-first: every key not listed is `Other`.

**F0 Scope and preconditions.** The rules apply to objects of revision `k` in these roles:
- (a) a terminal non-signature field (`/FT` `/Tx`, `/Btn` or `/Ch`, inherited allowed)
- (b) a widget kid (`/Subtype /Widget`, no `/T`) of one
- (c) the indirect `/AP` dictionary of such a widget
- (d) an appearance stream (`/N /D /R`) of a `/Tx` or `/Ch` widget

Every one of these preconditions must hold, else each change below is `Other`:
- the signed revision's AcroForm has no `/XFA`
- the evaluated signature has no FieldMDP (a `/Lock` on its field, or a `/Reference` FieldMDP)
- no widget of the field (the field merged with its widget, or a widget kid) sets NoZoom (8), NoRotate (16) or a reserved bit in its signed `/F`, and that `/F` is a readable integer (QA round 2 finding 32; `geometry::form_widget_flags_ok`). §12.5.3: such a widget is drawn at a fixed size or upright at its `/Rect`'s upper-left corner, outside the `/Rect`, so filling it is `Other` whatever the page's rotation. Hidden, NoView and the other flags a form widget carries stay allowed: the fill shows nothing the signed widget did not show
- each use of the object in `k` is an expected context. Those are a `/Fields` or `/Kids` entry; a page's `/Annots`; its widget's `/AP`; or an `/OBJR` dictionary's `/Obj` in the structure tree (D-24, pyHanko's `_find_in_structure_tree`). Field-tree `/Parent` links are ignored, as in M3.
- the role is still in force in `r`: the field is still in the tree and the widget is still in its page's `/Annots`
- every object these rules read in `k` (the field, its ancestors, its widgets, their `/AP` and `/AP /N` dictionaries) passes the canonical-input gate (V10, manager ruling R-12 (2); QA round 3 finding 5), and so does `k`'s copy of every object the revision changes

**F1 Field object.**
- Only `/V` may change.
- On a merged field/widget, `/AS` (F3) and `/AP` (F4) may change too.
- `/V`:
  - `/Tx`: a direct string, or removed.
  - `/Ch`: a direct string or a direct array of strings, or removed.
  - `/Btn` without the Pushbutton flag (`/Ff` bit 17): a direct name, or removed.
- These are always `Other`:
  - a Pushbutton
  - a field with ReadOnly (`/Ff` bit 1) in `k`
  - any other key: `/DA /Q /Ff /F /DV /TU /TM /MaxLen /Opt /I /TI /RV /DS /MK /Rect /AA /T /FT /Kids /Parent /Type` and so on

**F2.** A new `/V` is never an indirect reference.

**F3 `/AS`** (`/Btn` widgets only):
- The new value is `/Off` or a key of that widget's `/AP /N` dictionary **in revision `k`**.
- It is consistent with the field's `/V` in `r`:
  - checkbox: `/AS == /V`, or `/Off` when `/V` is `/Off`
  - radio: the kids whose `/N` has state `/V` get `/V`, the others `/Off`
- A `/Btn` widget's `/AP` never changes.

**F4 `/AP`** (`/Tx` and `/Ch` widgets, and only when the field's `/V` in `r` differs from `k`):
- The new `/AP` is a direct dictionary, or a new object (pyHanko's `compare_key_refs`).
- `/N` is required.
- `/N` and the optional `/D` and `/R` are new streams, or the same stream changed in place (F5).
- A new stream is a form XObject (`/Subtype /Form`) with a direct `/BBox` of four finite numbers (with an area when the widget is visible) and, if any, a `/Matrix` of six finite numbers (invertible when visible). QA round 1 finding R5: PDFium does not clip an appearance without `/BBox` to the widget. Every `/BBox` and `/Matrix` number is within ±10^5 (`geometry::MAX_GEOMETRY_MAGNITUDE`; QA round 4 finding 4: a `/Matrix` translating by 2,147,483,647 is placed elsewhere by PDFium, which maps it in single precision; `form_fill_ap_matrix_magnitude`), and so are the four `/BBox` corners mapped through the `/Matrix` (manager ruling R-21, QA round 5 findings 28 and 31: a `/BBox [0 0 1 1]` translated by 10^7 was drawn 1,590 pixels outside the field by PDFium; `form_fill_ap_matrix_small_bbox`). ISO 32000-2 Annex C limits user space to 14,400 units, so the bound refuses nothing a conforming writer produces. When the widget is visible, the mapped box's largest coordinate times its scale onto the widget's `/Rect`, `max(Rw / Mw, Rh / Mh)`, is at most 2^20 (`geometry::MAX_APPEARANCE_AMPLIFICATION`; final fix round 2, findings 2 and 4: PDFium's `CFX_Matrix::MatchRect` maps in single precision, so a `/BBox [0 0 0.01 0.01]` translated by 99,999 was drawn 2,100 pixels outside the field although every number is within ±10^5; `form_fill_ap_tiny_bbox_translate_1e5`, `form_fill_ap_matrix_tiny_bbox`, `tiny_boxes_qa_tried`). A `/Rect` that cannot be read counts as the largest the bound allows.
- An indirect `/AP` dictionary of `k` that changes must be used once.

**F5 In-place appearance stream.** A stream of `k` that is the `/AP /N|/D|/R` of exactly one `/Tx` or `/Ch` widget, and is used nowhere else (M3 usage index; in every reader: the index walks the raw references of objects that are not canonical too, QA round 4 finding 1), may change when that field's `/V` changes. This is pyHanko's `_allow_in_place_appearance_update`. The rewritten stream must keep a valid form XObject dictionary (F4).

**F6.** New objects reachable from a changed `/V`, `/AP` or appearance stream through new objects (`new_dependencies`) are explained at `FormFilling`.

**F7.** AcroForm `/DR` may only gain names: the M3 V10 (3)(c) rule. Since QA round 1 (finding 9) a gained name must also be unused by every signed appearance stream (of every widget and annotation on every page, every state), read with every content stream it draws, nested: form XObjects, tiling patterns and Type 3 glyph procedures with the Type 3 font's resources (QA round 2 finding 22), and since QA round 3 (findings 6 and 21) the graphics states it sets: an `/ExtGState` `/SMask` dictionary's `/G` transparency group (§11.6.5.2) and the Type 3 font of an `/ExtGState` `/Font` entry (Table 57), besides every signed `/DA`. Since QA round 4 (finding 12) a form XObject or Type 3 font is recognized by its `/Subtype` read through a reference too (readers dereference it; a stream without a readable subtype that has a `/BBox` is read as a form), and when a stream it reads has no `/Resources` of its own (an appearance, form, pattern or Type 3 font), the content streams the resources of every page draw are read too (§7.8.3: such a stream's names resolve in the page's resources; each page-tree node's resources once). Since QA round 5 (finding 29) that also holds when the stream's own `/Resources` lack any of the categories `/ExtGState`, `/ColorSpace`, `/Pattern`, `/Shading`, `/XObject`, `/Font` and `/Properties` (PDFium looks a name its category lacks up in the page's resources: `form_dr_adds_name_used_in_ap_ownres_empty`, `_ownres_font_only`), and the page resources are collected along both inheritance walks (§7.7.3.4): every page's `/Parent` chain (PDFium) and the `/Kids` walk from the catalog's `/Pages` (poppler), so a node only one of them reaches is read too (`form_dr_adds_name_used_in_ap_parent_mismatch`). An object is read once per role (appearance, form, pattern, glyph, soft-mask group, font, graphics state, resource dictionary, category dictionary, glyph map), so a dictionary shared by two categories, or a `/CharProcs` map shared by a font and a category, is read in each. A name counts both decoded and as written (`/F#31` and `/F1`). The signed objects the guard read, and the signed `/DR`, pass the canonical-input gate when a name is added (R-12 (2)). Names that only page content uses are not read: viewers resolve those in the page's resources, never in `/DR`. A viewer that does not find a name in a stream's own `/Resources` or in the page's may fall back to `/DR` (§0.3); a name some signed stream draws is never new there.

**F8.** Never allowed: adding or removing fields or widgets, moving a widget (`/Rect`), changing `/Fields`/`/Kids` except M3's signature-field appends, or changing a page except §5.2 and M3 appends.

**Attack variants these rules must resist** (corpus §5.4):
- widget flag hide or unhide
- `/Rect` moved over signed text
- `/DA` restyled to white, `/Q`, `/Ff` Password or Comb
- `/AP` changed with `/V` unchanged
- checkbox "On" appearance replaced
- `/AS` set to an unsigned state
- a ReadOnly field filled
- a value change in an XFA document
- `/V` as an indirect reference to an existing string object
- an in-place `/AP` stream that is also the page's or another widget's appearance
- `/MK`, `/DV`, `/TU`, `/Opt`, `/I` or `/RV` changed
- a kid widget added to a field
- an orphan widget (on a page, not in `/Fields`) given a new `/AS` or `/AP`
- a widget used both as a field kid and as another field
- a value filled in a document whose evaluated signature carries FieldMDP
- a tagged form (OBJR context) filled legitimately: a **control** case, `FormFilling`

### 5.2 Annotations whitelist (rule V10 (9); level `Annotations`; class `Annotation`; only if D-1)

**A1.** A **new** object (a new number, never listed) appended at the end of an existing page's `/Annots` (the page or an indirect array, as M3's rule 5) with:
- `/Subtype` ∈ {`Text`, `FreeText`, `Line`, `Square`, `Circle`, `Polygon`, `PolyLine`, `Highlight`, `Underline`, `Squiggly`, `StrikeOut`, `Caret`, `Ink`, `Stamp`}, or a `Popup` (A4)
- `/P`, if present, equal to that page

**A2 Allowed keys and appearance.** Every new markup annotation (not a Popup) has an `/AP /N` that is a new form XObject as F4 requires (R-2: no viewer then synthesizes an appearance; a Text annotation without one is a fixed-size icon in poppler). A Text annotation is allowed only on a page whose effective `/Rotate` (its own, else inherited, §7.7.3.4) is a multiple of 360 (QA round 2 finding 7; §12.5.6.4: Text is drawn as if NoZoom and NoRotate were set, so on a rotated page viewers paint it outside its `/Rect`; §0.2). Since QA round 3 (manager ruling R-13, finding 11) the page must be one every reader places the same way: reached exactly once by the `/Kids` walk from the catalog's `/Pages`, with a `/Parent` chain that is the reverse of that walk, and the effective `/Rotate` is the one inherited along the walk (V10); this holds for every annotation and signature widget a page's `/Annots` gains, not only for Text. Its geometry lies inside its `/Rect` (R-2; `revisions/geometry.rs`):
- `/QuadPoints` (text markup) inside the `/Rect` shrunk by a quarter of each quadrilateral's height plus 0.5 (poppler regenerates Highlight caps from `/QuadPoints` even with an `/AP`, and they reach that far);
- `/InkList`, `/L` (with its leader lines `/LL /LLE /LLO`, and no `/Cap true` caption), `/Vertices`, `/Path` and `/CL` inside the `/Rect` shrunk by half the border width (and by the line endings' reach when `/LE` is set);
- `/RD` four non-negative insets that fit the `/Rect`; `/BE` only `/S /S` (no cloudy border);
- a `/Rect` of four finite numbers with an area, written canonically like every number the decision reads (R-12, V10; QA round 3 finding 12: PDFium reads a coordinate of `4294967296` as 0), each within ±10^5 (QA round 4 finding 13, R-21), as are its appearance's `/BBox`, its `/Matrix` and the `/BBox` mapped through the `/Matrix`, mapped onto the `/Rect` within the precision bound (F4), and every geometry number below.
- every geometry entry (`/QuadPoints`, `/InkList` and its paths, `/L`, `/Vertices`, `/Path` and its segments, `/CL`, `/RD`) is a **direct** array of direct finite numbers, and the numbers one annotation gives are capped; the geometry read for all annotations of a comparison is charged to the classifier's work budget (QA round 2 finding 1: shared indirect arrays made the check quadratic). `/Border` has at most four entries and `/LE` at most two.

Only these keys:
- **common** (§12.5.2): `Type Subtype Rect Contents P NM M F AP AS Border C BS CA ca BM Lang`
- **markup** (§12.5.6.2): `T Popup RC CreationDate IRT Subj RT IT`
- **per subtype:**
  - Text: `Open Name State StateModel`
  - FreeText: `DA Q DS CL BE RD LE`
  - Line: `L LE IC LL LLE Cap LLO CP CO`
  - Square/Circle: `IC BE RD`
  - Polygon/PolyLine: `Vertices LE IC BE Path`
  - text markup: `QuadPoints`
  - Caret: `RD Sy`
  - Ink: `InkList Path`
  - Stamp: `Name`
  - Popup: `Parent Open`

Anything else is `Other`, in particular `A AA OC StructParent ExData Measure FT Kids V Parent` (except on a Popup).

**A3.** `/F` may set only Invisible (1), Print (4), ReadOnly (64), Locked (128) and LockedContents (512). Hidden (2), NoZoom (8), NoRotate (16), NoView (32), ToggleNoView (256) and the reserved bits are `Other`: no print-only content, and no fixed-size or unrotated drawing outside the `/Rect` (R-2). New signature widgets have the same whitelist (R-3, §5.3).

**A4.** A Popup's `/Parent` is a new A1 annotation of the same revision, on the same page.

**A5.** `/IRT` refers to an annotation listed in some page's `/Annots` in `r`. Its `/AP` dependencies that are new objects are explained at `Annotations`.

**A6.** Existing annotations: any change or removal is `Other`. That is stricter than ISO P = 3, which also allows modify and delete, and equal to pyHanko.

**A7.** Existing `/Annots` entries keep their order: a prefix.

**Attack variants:**

- `/OC`
- NoView on a printing annotation

- an existing annotation removed or re-pointed
- `/Annots` reordered
- a new annotation reachable from a changed catalog instead of `/Annots`
- a new annotation in a revision that also changes `/Rotate`

  - none of its own for a document timestamp: its `docmdp_ok` is `None` (R-5), but its modification analysis runs with the P in force at it, the smallest P of the signatures that set one and end at or before it, else 2 (manager ruling R-20, QA round 5 finding 14: a markup annotation after a timestamp in a P = 1, P = 2 or uncertified document is `Other`, as in pyHanko; `certify_p1_doc_timestamp_then_markup`, `certify_p2_doc_timestamp_then_markup`, `approval_doc_timestamp_then_markup_is_other_for_the_timestamp`; under P = 3 it stays `Annotations`, `certify_p3_doc_timestamp_then_markup`)

  ```
  docmdp_ok = Some(match P_effective {
      1 => classes ⊆ {Relisting, Orphan, XrefStream, DocTimeStamp},          // D-2 (DSS joins in M11)
      2 => modification <= FormFilling,
      3 => modification <= Annotations,                                     // D-1; else <= FormFilling
  })   // modification Other ⇒ false for any P (incl. Unclear/ContiguousBlockFromStart coverage, as pyHanko)
  ```
  pyHanko computes approvals as `mod != OTHER`. Ours equals that wherever pyHanko's vocabulary is reached (pyHanko never emits `ANNOTATIONS`), and is stricter elsewhere.
- **C3 window** (R-7): each signature is judged over its own window `k..r`. An approval signed after a P = 3 certification gets `P_effective = 3`, so a later markup annotation is `Annotations` with `docmdp_ok` true for it too (§0.2 row `certify_p3_approval_then_markup`).
- **Document timestamp bookkeeping** (class `DocTimeStamp`, not `Metadata`): the `/Info` `/ModDate` and `/Producer`, the catalog's `/Version` and ESIC developer extension, and the XMP packet's `xmp:ModifyDate` and `pdf:Producer` values. Manager ruling R-8 (QA round 1 findings 24, 32): exempt only when the revision that adds the document timestamp wrote the object and no later revision of the window rewrote it; the same edit in a revision without a timestamp is `Metadata`. The revision that adds a document timestamp is the first in the window that lists its dictionary: re-listing the dictionary in a later revision does not make that revision's bookkeeping exempt (QA round 2 finding 21).

- **Who:** a QA reviewer who is not an M4 developer and not this brief's author, in a dedicated pass.

- **Working method:** read-only, with files crafted under `/tmp` only.

  - (4) every V7b and V7c step

## 8. Open decisions: all accepted by the manager on 2026-10-11 as recommended (DECISIONS D13)

> Manager note on staging: in stage 0, Dev A builds `folioxide-content` completely (builder, standard14 + AFM tooling + NOTICE, WinAnsi encoding, JPEG header parsing) in parallel with Dev B's skeleton. Dev B therefore does NOT create the `folioxide-content` stubs; Dev A owns that crate from stage 0.

1. **D-1, Annotations level:**
   - **Recommend** the add-only markup whitelist of §5.2, recorded as the *only* "more lenient than pyHanko" exception to D10.1, with the rows of §0.2. Without it, every P = 3 document with reviewer comments shows a broken certification.
   - **Alternative:** keep annotations `Other`, as in pyHanko.
2. **D-2, P = 1 strictness:**
   - **Recommend** allowing only re-listings, orphans, cross-reference streams and document timestamps; `/Info` and XMP changes give `docmdp_ok = false` (stricter than pyHanko).
   - ROADMAP M4 acceptance #3 says "`docmdp_ok=False` for P = 1 followed by an incremental Info change". pyHanko 0.37.0 reports **`True`** there (probe). Reword it to "P = 1 + form fill: `docmdpOk` false (pyHanko and ours); P = 1 + Info change: ours false, pyHanko true (deliberate)".
3. **D-3:** refuse to create a new **visible** signature field on certified documents (P = 2 or 3) with `DocMdpForbids`. Existing empty visible fields and invisible approvals stay allowed.
4. **D-4:** the TSA certificate rule is OpenSSL's `check_purpose_timestamp_sign`. A failure makes the token **invalid** (not just untrusted) and blocks B-T.
5. **D-5:** several tokens are accepted (EN 319 142-1: cardinality ≥ 1). The earliest sound and trusted one is selected, and all are listed.
6. **D-6:** timestamp problems live in `TimestampInfo`, so the signature's `is_valid()` is not affected by unsigned data.
7. **D-7:** the signer is validated at a trusted `genTime` when no validation time is given.
8. **D-8:** `DEFAULT_TSA_RESERVE = 8192` and one full retry on overflow.
9. **D-9:** `grantedWithMods` is accepted. pyHanko's signer accepts only `granted`, but RFC 3161 §2.4.2 allows it.
10. **D-10:** a nonce is mandatory: random via `sys-rng`, or set by the caller. Nonces are compared as INTEGER values.
11. **D-11:** requests use SHA-2 with NULL parameters (as `openssl ts -query`), and the imprint digest defaults to the signature's digest.
12. **D-12:** BER tokens are embedded verbatim with a warning.
13. **D-13:** `docmdp_ok` is always computed (`P_effective`), and `is_acceptable` requires `docmdp_ok != Some(false)`. This changes the semantics of an M3 API before 1.0.
14. **D-14:** the form-fill deviations from pyHanko of §0.1: `/F`, `/DA`, `/Q`, `/Ff`, `/AP` without `/V`, `/Btn` `/AP`, ReadOnly, XFA, own FieldMDP, unknown `/AS` states, indirect `/V`.
15. **D-15:** the problems `CertificationNotFirst` and `DocMdpInvalid`.
16. **D-16:** fonts are Helvetica and Helvetica-Bold, with WinAnsi and `?` replacement. `/Widths` are written. AFMs come from PDFBox 3.0.3 resources, with the Adobe notice in `NOTICE` files.
17. **D-17:** JPEG is limited to SOF0/1/2, 8-bit, 1 or 3 components. CMYK is `Unsupported` until M7.
18. **D-18:** the appearance rect is in default user space, with rotation compensation. An existing field's `/Rect` is never changed. Existing fields with a separate widget plus an appearance are `Unsupported`.
19. **D-19:** `PendingTimestampVerification` is retired: kept in the enum, never emitted.
20. **D-20:** B-T reached through a later document timestamp is deferred to M11.
21. **D-21:** MockTsa lives in the testkit and signs through a closure. The testkit gains `sha2`. The TSA certificate variants come from `gen-pki.sh --tsa-variants`, which issues them from the existing root key with `tsa.key.pem` and leaves every existing file unchanged: `tsa-eku-noncritical`, `tsa-no-eku`, `tsa-eku-extra`, `tsa-ku-keyenc`, `tsa-not-yet-valid`.
22. **D-22:** oracle runner keys `renderProbes`, `timestamp: "invalid"` and `timestampTrusted`. These change A.9 and D7.6.
23. **D-23:** with `/XFA`, or with the evaluated signature's own FieldMDP, generic form filling is `Other` until M11.
24. **D-24:** a structure-tree `/OBJR /Obj` reference is an allowed context for fields and widgets, as in pyHanko.
